# V4.0 迁移审查与实施计划

本文保留 P0/P1 时的工程审查与初始迁移方案。三兽像素素材接入后的当前状态、后续分轮范围和验收标准，以 [后续开发计划](DEVELOPMENT-PLAN.md) 为准；已完成的显示接入见 [像素验收](PIXEL-IMPORT-REPORT.md)。

## P0 实际工程审查

项目不是空壳。`Game` 承担固定 60Hz 循环、原 Player 移动、碰撞、正交相机跟随、UI 生命周期和暂停重开；`Input` 有虚拟摇杆、键盘与旧冲刺/装饰跳跃；`Combat` 是不依赖 DOM/Three.js 的敌人池、索敌、投射物、接触伤害、经验磁吸和统一 `damageEnemy`；`Progression` 管经验曲线、强化数据和选卡队列；`CombatView` 批量实例渲染敌人/投射物/效果；`world.ts` 生成固定种子轻量地形和圆形障碍；`Monster` 保留程序几何、旧 Sprite、GLB 三条加载路径；`camera-25d.ts` 负责屏幕到地面的输入映射；`ui.ts` 与 `style.css` 管菜单、HUD、升级、死亡和设置。没有独立的 Player/EnemySystem/ExperienceSystem/UpgradeSystem 类，也没有波间商店或真实随机区域逻辑。

现有 `trial.ts`、`challenge.ts` 是旧冲锋试炼及有限三波挑战，不能当作正式六波玩法。旧 Sprite 是已有视觉实验，不等于正式像素资源。敌人目前有最多 48 个的全量两两避让，当前 P1 不扩大敌人规模；P7 密度提升前必须改为空间网格局部查询。经验、效果、投射物已有固定容量池。金币尚未实现。

审查时存在未提交的 `combat.ts/game.ts/style.css/trial.ts/ui.ts` 修改、新的 `challenge.ts` 与挑战测试，以及多张截图；这些全部先进入安全快照，未覆盖、暂存或重置用户工作区。

## P1 最小架构

- `party.ts`：纯逻辑物种定义与实例、最多三只的 PartySystem（容量设计预留四只）、独立冷却/攻击统计/阶级/进化状态、统一基础属性计算、伙伴跟随。共享生命继续由 `Combat.hp` 唯一保存，实例不设独立生命。主控位置沿用 `Game` 原有移动与碰撞，提交给编队受控实例；伙伴绝不反向推动主控。
- 跟随：小编队阵型偏移、局部圆障碍滑动与侧向绕行，有限候选落点，长距离或卡住时重定位到主控附近有效落点；没有每帧导航网格或全地图寻路。保留上帧位置用于插值。
- `Combat`：可选编队上下文；编队中从各自位置独立索敌、计时和发射，投射物继续使用原池、扫掠碰撞、统一 `damageEnemy` 与经验掉落。原单兽分支保留以回归验证，不复制一套战斗世界。
- `party-view.ts`：仅伙伴的廉价彩色占位几何、脚影与插值显示。主控复用现有焰绒与脚环。它不承担 P2 像素资源加载；旧 GLB 与 Sprite 路径完整保留。
- `Game/UI/Input`：新增主要“三兽编队原型”入口和编队信息；原型隐藏并禁用冲刺与跳跃，只有摇杆。旧单兽/犄角/挑战为兼容入口。本轮不更改旧地图、经验数值和既有升级卡；继承旧被动法术仍围绕主控结算。
- 生命周期：开始/重开重置实例、冷却、位置及所有旧池；暂停/选卡/后台/死亡停止逻辑；销毁时释放占位资源。原型不是正式六波挑战，暂不提供正式通关。

## P2 需要的素材

三物种的基础形态透明 PNG 或 Sprite Sheet、每帧尺寸/间距/顺序、脚底锚点、朝向约定、待机与移动帧和帧率；如有攻击动作同时提供。推荐统一像素密度与固定画布，至少清晰区分火/水/草。阶级 III 与完全体素材可后续交付。还需确认授权/原创归属；敌人/Boss 和 UI 像素边框可在相应阶段逐步提供，不要求本轮备齐。
